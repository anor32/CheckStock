# CheckStock

Тестовое задание: веб-прототип учёта остатков для одного магазина с двумя и более складами фулфилмента (ФФ). Показывает остатки по артикулам и складам, операции прихода/перемещений/резерва и отгрузок FBS/FBO, а также историю операций.

## О проекте (тестовое задание)

- **Формулировка ТЗ:** [`agents/tasks/TASK_full.md`](agents/tasks/TASK_full.md), исходное задание — [`agents/redirect_spec_extracted.txt`](agents/redirect_spec_extracted.txt).
- **Что реализовано:** экран остатков (физически/резерв FBS/доступно по каждому артикулу и ФФ), справочники товаров и складов, CRUD складов со soft-delete, операции прихода, перемещения между ФФ, FBO out/receive, FBS reserve/ship/cancel, журнал движений и статусы «в пути» (между ФФ, FBO, к клиенту по FBS), идемпотентность операций по `idempotency_key`, обработка нехватки на выбранном ФФ с диагностикой по другим активным складам, веб-интерфейс (статический фронтенд в `frontend/`, отдаётся приложением).
- **Проверки качества:** `uv run pytest -q`, `uv run ruff check .`, `uv run mypy src` (также `uv run mypy src tests`), запуск через Docker Compose, smoke-проверка API/UI.
- **Тестовые данные из ТЗ:** склады **Север** и **Юг**, артикулы **SKU-101/102/103** с количествами после тестового прихода (см. раздел ниже и `src/infrastructure/fixtures.py`). При старте контейнера API автоматически применяет миграции и загружает фикстуры (`bin/run_api`).

## Архитектура и ключевые решения

Проект построен по слоям Clean Architecture (`src` layout):

- `src/domain` — сущности (`Product`, `Warehouse`, `Stock`, `Movement`), доменные исключения и интерфейсы репозиториев/UoW. Домен не зависит от инфраструктуры и API.
- `src/application` — use cases и DTO прикладного слоя. Бизнес-сценарии (приход, перемещение, приёмка, FBO-out/receive, FBS reserve/ship/cancel и т.д.) оркестрируют операции через интерфейсы.
- `src/infrastructure` — реализации репозиториев, Unit of Work, ORM-модели SQLAlchemy, настройки БД, Alembic, сиды/фикстуры.
- `src/api` — FastAPI-роуты, схемы запросов/ответов, DI/composition root, статика UI.

Ключевые решения:

- **Модель остатков:** `Stock` хранит `qty_physical` и `qty_reserved_fbs` по паре (товар, склад); `qty_available = qty_physical - qty_reserved_fbs`.
- **Журнал операций:** `Movement` фиксирует тип, количество, направление (откуда/куда), статус и время. История операций формируется из журнала движений.
- **Склады:** удаление ФФ — soft-delete (`is_deleted`, `deleted_at`), чтобы сохранить остатки и историю; такие склады/остатки могут отображаться в интерфейсе.
- **Перемещения между ФФ:** отправка создаёт движение в статусе «в пути» (`in_transit`) и списывает физический остаток со склада-отправителя; приёмка увеличивает остаток склада-получателя и завершает движение.
- **FBO:** отправка со склада уменьшает остаток на ФФ и создаёт движение в пути до приёмки; приёмка FBO завершает движение.
- **FBS:** резерв увеличивает `qty_reserved_fbs` на выбранном складе (`type=fbs_reserve`, `status=pending`). Отгрузка (`POST /movements/{id}/fbs-ship`) списывает физический и зарезервированный остаток со склада и переводит движение в «в пути к клиенту» (`type=fbs_ship`, `status=in_transit`, `completed_at=null`) — такая запись доступна в `/api/v1/movements` и используется для отдельной категории блока «Товары в пути» (FBS к клиенту). Подтверждение доставки в прототипе не предусмотрено, поэтому статус остаётся `in_transit`. Отмена резерва снимает резерв.
- **Идемпотентность:** операции создания/подтверждения поддерживают `idempotency_key` (в теле запроса) для защиты от повторного применения; повторное подтверждение не приводит к повторному списанию/изменению остатков.
- **Ошибки:** доменные ошибки маппятся в HTTP-ответы формата `{ "detail": "..." }`; недостаток/конфликты операций возвращают `409`, отсутствие сущностей — `404`. При нехватке на выбранном ФФ `detail` содержит доступно/запрошено на выбранном складе и суммарную доступность по другим активным ФФ (с указанием, достаточно ли её, и списком складов-кандидатов при достаточности). Автосплит/автоперемещение не выполняются.

## Быстрый старт

### 1. Установка зависимостей

```bash
uv sync
```

### 2. Настройка окружения

Создайте `.env` (см. `.env.example` при наличии) и задайте параметры подключения к PostgreSQL (`DATABASE_URL` и/или переменные, используемые в `src/infrastructure/settings.py`).

### 3. Миграции и тестовые данные

```bash
uv run alembic upgrade head
uv run python -m src.infrastructure.fixtures
```

### 4. Запуск API

Локально:

```bash
uv run uvicorn src.api.main:app --host 0.0.0.0 --port 8000
# или
uv run python run.py
```

Через Docker Compose:

```bash
make start
# пересборка + запуск
make rebuild
```

Проверка: `http://localhost:8000/` (UI), `http://localhost:8000/docs` (Swagger), `GET /` (health-check).

## Проверка основных сценариев

Рекомендуемый порядок проверки на тестовых данных (Север/Юг):

1. **Остатки:** открыть экран остатков и убедиться, что отображаются SKU-101/102/103 по складам Север/Юг с количествами как в таблице выше (физически, доступно, резерв FBS).
2. **Приход:** оформить приход товара на выбранный ФФ и проверить обновление остатков и запись в истории.
3. **Перемещение между ФФ:** отправить перемещение (остаток списывается с отправителя, товар в пути) и выполнить приёмку (остаток появляется у получателя, движение завершается).
4. **FBS:** создать резерв (увеличивается резерв, уменьшается доступно), затем выполнить отгрузку и проверить, что физический остаток и резерв на ФФ списаны, а в `/movements` появился `fbs_ship` со статусом `in_transit` («в пути к клиенту», отдельная категория блока «Товары в пути»). Либо выполнить отмену резерва и проверить снятие резерва.
5. **FBO:** отправить товар по FBO (списание с ФФ, статус «в пути» до приёмки) и подтвердить приёмку, проверить историю.
6. **Удаление ФФ (soft-delete):** удалить склад с остатками/историей и убедиться, что остатки и история сохраняются и склад/товар отображаются как числящиеся на удалённом ФФ.
7. **Нехватка на выбранном ФФ:** попытаться зарезервировать/отправить/переместить больше, чем доступно на выбранном ФФ — операция должна быть отклонена (ожидается `409` с `detail`), остатки не должны измениться. Если суммарно по другим активным ФФ товара достаточно, `detail` явно указывает на это (с суммой и складами-кандидатами); при общей нехватке `detail` сообщает, что суммарно недостаточно. Операция на выбранном ФФ всё равно недоступна без перемещения/выбора другого склада.
8. **Повторное подтверждение (идемпотентность):** повторить POST-операцию с тем же `idempotency_key` — повтор не должен списывать/изменять остатки дважды.

## API v1 (основные эндпоинты)

Базовый префикс: `/api/v1`.

- **Справочники:** `GET /products`, `GET /warehouses`
- **Склады:** `POST /warehouses`, `PATCH /warehouses/{id}`, `DELETE /warehouses/{id}` (soft-delete)
- **Остатки:** `GET /stocks`, `GET /stocks/{product_id}/{warehouse_id}`
- **Движения:** `GET /movements`, `GET /movements/{id}`
- **Операции (POST, с `idempotency_key` в теле):** `/movements/inbound`, `/movements/transfer`, `/movements/{id}/receive`, `/movements/fbo-out`, `/movements/{id}/fbo-receive`, `/movements/fbs-reserve`, `/movements/{id}/fbs-ship`, `/movements/{id}/fbs-cancel`

### Контракт движений FBS «в пути к клиенту»

- После успешной отгрузки резерва FBS (`/movements/{id}/fbs-ship`) соответствующее движение представлено как `type="fbs_ship"`, `status="in_transit"`, `completed_at=null` (товар списан со склада ФФ и находится в пути к клиенту).
- Для фильтрации/отображения категории «Товары в пути → к клиенту (FBS)» фронтенд может использовать записи `/movements` с `type=fbs_ship` и `status=in_transit`.
- Другие категории «в пути»: перемещения между ФФ — `transfer_out` + `in_transit`, FBO — `fbo_out` + `in_transit`.

Подробные схемы — в Swagger UI (`/docs`) и в `src/api/schemas.py`, `src/api/routes/`.
